006.7. Introduce Project Issue Register and Dependency Checks
Objective
Introduce a lightweight, centralised issue-management process for the UK Rental Forecasting Project.
The purpose is to ensure that important findings, unresolved methodological decisions, data-quality limitations, and implementation dependencies are not forgotten as development progresses from data ingestion to preprocessing, feature engineering, modelling, and deployment.
Implement this through:
1.	A single issue register at docs/issue-register.md.
2.	Permanent issue-management instructions in AGENTS.md.
3.	A simple task-level dependency-checking process.
The system must prevent unresolved critical issues from being overlooked without unnecessarily blocking unrelated development.
Do not introduce additional tools, dependencies, databases, or monitoring infrastructure.
1. Review Existing Project Context
Before making changes:
•	Read AGENTS.md and docs/ENGINEERING_STANDARDS.md.
•	Review docs/data-architecture-and-dictionary.md, particularly Task 006.2 findings and outstanding decisions.
•	Review relevant existing audit reports, task documentation, and supporting evidence.
•	Check the current repository structure and conventions.
•	Preserve all existing project instructions and approved methodological decisions.
Use the repository as the source of truth.
Do not invent issues or treat unverified assumptions as established findings.
2. Create Central Issue Register
Create:
docs/issue-register.md
Use a concise Markdown table containing:
Field	Description
Issue ID	Unique identifier, e.g. ISS-001
Issue	Concise description of the outstanding issue
Category	Data Quality, Methodology, Data Availability, Geography, Engineering, or Other
Affected Area	Relevant dataset, feature, component, or development stage
Required Before	The task or development stage by which resolution is required
Status	Open, In Progress, Resolved, or Deferred
Required Action / Decision	What must be investigated, implemented, validated, or approved
Evidence Reference	Link to the relevant project documentation or supporting evidence
Additional requirements:
•	Use stable issue IDs.
•	Keep descriptions concise and actionable.
•	Avoid duplicating detailed research findings already documented elsewhere.
•	Link to supporting evidence rather than reproducing it.
•	Distinguish unresolved decisions from known data limitations.
•	Do not automatically classify all data-quality concerns as blockers.
•	Preserve resolved issues as a historical decision record.
•	Avoid creating separate issue files for individual datasets.
Where an issue requires project-owner approval, explicitly identify that requirement.
Where appropriate, include a short resolution note documenting the approved decision and supporting evidence.
3. Populate the Initial Register
Review the existing repository and identify outstanding issues that may affect future development.
Pay particular attention to findings from Task 006.2, including:
•	Median earnings measurement and definition.
•	Survey-based versus modelled unemployment.
•	Local Authority geographic compatibility and boundary changes.
•	Historical publication dates, release vintages, and point-in-time availability.
•	Historical mortgage-rate methodology changes.
•	Household and student population definitions.
•	Housing-supply numerator and dwelling-stock denominator compatibility.
•	Planning application counts versus approved dwelling units.
•	Incomplete historical or geographic coverage.
•	Other material unresolved findings documented in the repository.
Consolidate related findings where they represent the same underlying decision or dependency.
Do not create an issue for every individual missing observation, outlier, or minor source-data anomaly.
Retain detailed data-quality measurements in their existing source-specific reports.
For each issue, identify the earliest development task or stage where action is genuinely required.
Do not assume every unresolved issue must be resolved before the next ingestion task.
4. Update AGENTS.md
Add a concise section titled:
Project Issue Register and Dependency Management
The instructions must require Codex to follow these rules.
Before Starting a Development Task
1.	Review docs/issue-register.md.
2.	Identify unresolved issues relevant to the current task.
3.	Determine whether each relevant issue:
o	Does not block the task.
o	Can be addressed safely within the authorised task scope.
o	Requires resolution or project-owner approval before proceeding.
4.	Review detailed supporting documentation only when necessary.
5.	Do not silently make methodological decisions to bypass unresolved issues.
Decision Rules
Proceed
Continue when no unresolved issue prevents reliable execution of the current task.
Proceed with documented limitations
Continue when relevant issues can be preserved, investigated, or safely handled within the approved scope without making unauthorised methodological decisions.
Record applicable limitations and follow-up actions.
Blocked — Approval Required
Stop the affected implementation when an unresolved issue requires a material methodological decision, an unapproved data substitution, or a prerequisite necessary for correct execution.
Clearly report:
•	The relevant issue ID.
•	Why it blocks the task.
•	The decision or action required.
•	The available alternatives, where appropriate.
Do not block unrelated work unnecessarily.
If a task contains independent activities, Codex may proceed with unaffected activities while reporting the blocked components, provided this does not compromise correctness or the approved methodology.
After Completing a Development Task
1.	Review findings for newly discovered issues.
2.	Add material unresolved issues to the register.
3.	Update existing issue statuses when new evidence or decisions become available.
4.	Avoid duplicate or overlapping issues.
5.	Link new evidence to relevant documentation.
6.	Mark an issue Resolved only when the required action, validation, and any necessary approval have been completed.
7.	Preserve the record of resolved methodological decisions.
Include a brief issue-management summary in the final task report:
•	Relevant issues reviewed.
•	New issues identified.
•	Issues resolved or updated.
•	Remaining blockers or decisions requiring approval.
Efficiency Requirements
Keep issue checks lightweight.
Do not read every historical task document or entire research report for every development task.
Use the issue register to identify relevant dependencies, then inspect detailed evidence selectively.
Avoid unnecessary repeated analysis of previously verified findings.
Do not introduce automated issue-management infrastructure solely to enforce this process.
5. Issue Lifecycle and Governance
Use these statuses consistently:
•	Open: Identified but not yet resolved.
•	In Progress: Investigation or resolution is underway.
•	Resolved: Required action and validation are complete, including project-owner approval where necessary.
•	Deferred: Resolution is intentionally postponed to a later task or development stage.
A Deferred issue must retain a clearly identified future checkpoint.
Deferral must not be used to bypass a prerequisite for the current task.
Codex may independently resolve routine engineering issues within an authorised task.
Material methodology, architecture, feature-definition, and data-substitution decisions remain subject to project-owner approval.
Do not mark an issue Resolved solely because an implementation was attempted or Codex believes its proposed solution is reasonable.
6. Implementation Constraints
•	Keep the solution simple, maintainable, and proportionate to the project.
•	Do not modify ingestion, preprocessing, feature engineering, modelling, or infrastructure code.
•	Do not introduce new Python dependencies.
•	Do not create a separate issue-tracking database or service.
•	Do not duplicate the Data Dictionary.
•	Do not modify approved forecasting objectives or methodology.
•	Preserve existing AGENTS.md instructions, including task archiving and execution-time tracking.
•	Use repository-relative links where practical.
•	Maintain clear separation between verified findings, proposals, and approved decisions.
Codex may independently determine minor formatting and documentation details consistent with these requirements.
7. Acceptance Criteria
The task is complete when:
1.	docs/issue-register.md exists and follows a consistent, concise structure.
2.	Material outstanding issues from the existing repository have been identified and recorded.
3.	Every registered issue has a unique ID and a supporting evidence reference.
4.	Issues identify the development task or stage where action is required.
5.	AGENTS.md includes permanent issue-review and maintenance instructions.
6.	The process clearly distinguishes blocking and non-blocking issues.
7.	Codex is instructed to request approval before material methodological decisions.
8.	Future tasks are required to update the register when significant new findings arise.
9.	Resolved issues retain appropriate decision and validation evidence.
10.	Existing project functionality and approved methodology remain unchanged.
11.	No unnecessary dependencies, infrastructure, or documentation duplication have been introduced.
Verify that internal Markdown links resolve and that the register is consistent with the existing Data Dictionary.
Archive the original task instructions according to AGENTS.md.
