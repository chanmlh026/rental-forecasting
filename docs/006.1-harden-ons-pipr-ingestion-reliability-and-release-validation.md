# 006.1. Harden ONS PIPR Ingestion Reliability and Release Validation

## Role and Objective

Act as a senior Python data engineer performing a focused reliability and code-quality improvement of the existing ONS PIPR ingestion pipeline.

Task 006 has been implemented successfully. The initial 21 October 2026 release produced 124,362 valid rent observations for 294 eligible English Local Authorities, with 1-, 2-, and 3-bedroom categories and no missing or duplicate target observations.

Your objective is to strengthen the existing implementation without redesigning it.

**Preserve all existing functionality, output schemas, project architecture and approved modelling decisions unless a change is strictly necessary to correct a verified defect.**

## 1. Review the Existing Implementation

Inspect:

- ons\_pipr.py

- test\_ons\_pipr.py

- 006-ons-pipr-ingestion.md

- configs/storage.toml

- configs/ons\_lad\_apr2025\_v2.csv

- Relevant README and architecture documentation.

Locate the actual files within the repository rather than assuming their directories.

Before changing code, identify which reliability concerns are genuine and which are already adequately handled.

Do not implement speculative fixes without checking the existing behaviour.

## 2. Strengthen Existing Release Reuse Validation

Review the logic used when an already ingested release is reused.

Verify:

- Raw workbook SHA-256 matches its recorded metadata.

- Processed and validated Parquet checksums match their manifests.

- Release identifiers and source metadata are consistent.

- Both required output layers are present and complete.

- Existing manifests describe the correct release.

- Reused outputs retain the expected schema and unique observation keys.

Determine whether additional Parquet content validation is necessary.

Implement appropriate checks without unnecessarily reprocessing the entire workbook on every rerun.

Never silently reuse corrupt, inconsistent or incomplete output.

Add tests that deliberately corrupt or modify an existing output and verify safe failure.

## 3. Improve Interrupted Publication Recovery

Review the current publication sequence for the validated and processed release directories.

Investigate the risk of interruption after one directory has been published but before the other is complete.

Implement a simple, safe recovery mechanism appropriate for a local filesystem.

Requirements:

- Never silently overwrite valid existing releases.

- Never delete an existing valid raw snapshot.

- Distinguish an incomplete publication from a conflicting completed release.

- Ensure a rerun can safely recover from a clearly identified interrupted publication.

- Avoid treating arbitrary existing files as safe to delete.

- Preserve validation and error reports.

- Use a release completion marker or another clearly documented mechanism if appropriate.

- Keep the solution simple and compatible with the existing storage architecture.

Add a test simulating interruption between publication of the validated and processed layers.

If full cross-directory atomicity is impossible, document the actual guarantee and recovery behaviour accurately.
