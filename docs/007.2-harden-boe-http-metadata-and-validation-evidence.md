## Correction report - 21 November 2026

### Finding, scope and dependency outcome

The independent review supplied by the project owner identified session-cookie
values in the committed Task 007 validation evidence. Codex confirmed two
`Set-Cookie` fields: IUMZID4's derived manifest retrieval metadata and the
audit-only CSV comparison retrieval metadata. Their values are not reproduced
in this report, test fixtures, audit output or journal.

The source was `fetch()` converting the complete response header collection
to a dictionary. Raw manifests persisted that dictionary; derived manifests
copied it; `verify_bundle()`, `ingest()`/CLI reporting and the validation script
could export it again, including when replaying old snapshots offline.
Request headers currently contain only a static browser user agent, but future
or injected request metadata also needs exclusion of cookies/authentication.
The Task 007.1 probe stores selected response metadata rather than the complete
header dictionary; no equivalent exposure was found in its five JSON files.

**Proceed with documented limitations:** this is an authorised security and
evidence correction with no source-methodology change. ISS-004 and ISS-005 remain
Open and unchanged; their source-publication and feature-definition limitations
do not block header exclusion. New ISS-020 records the concrete remaining
historical exposure and owner decision, rather than treating the correction as
permission to rewrite history.

### Implementation and preservation

`safe_http_headers()` uses an explicit case-insensitive allowlist, excluding
unknown headers by default. It retains only `Accept`, `Accept-Encoding`,
`User-Agent`, `Content-Type`, `Content-Length`, `Content-Encoding`, `Date`,
`Last-Modified`, `ETag`, `Cache-Control`, `Expires`, `Retry-After`,
`Transfer-Encoding` and `Vary` when present. Header names retain source casing.
Cookies, authentication headers, API keys and session/tracing identifiers are
not on the allowlist. Repeated and mixed-case cookie headers are excluded.

The filter is applied at HTTP capture and manifest publication. Recursive
`safe_http_metadata()` handles nested request/response/header dictionaries
at manifest-read and export boundaries, including the Task 007 audit exporter.
Checksums are verified against the saved files before the in-memory manifest
view is filtered. This preserves detection of source/output corruption.

Existing raw responses, all existing manifests and all validated/processed
Parquet files are preserved byte-for-byte. Older local manifests still contain
their originally captured headers; they remain ignored local evidence and
must not be copied directly into a report. Supported manifest reads and reruns
return filtered copies without modifying those files. Newly published metadata,
including data supplied by an injected downloader, is filtered before writing.
This changes HTTP metadata handling, not response bytes or data selection.

The committed Task 007 JSON has been regenerated with the safe exporter.
Its only semantic changes are header exclusions; all non-header fields,
checksums, source URLs/parameters, UTC retrieval intervals, rate observations,
revision counts, selected examples and reconciliation results are unchanged.
No raw data was downloaded or replaced for this correction.

### Git history assessment and recommendation (ISS-020)

The original evidence blob was introduced in
`f73119a05b6eea046c61cac47954f19e9797da48` and is also reachable through
`321962d0683a1e01953115e8b9f2e555cb8dd3b6`. A normal correction commit removes
the values from the current file but does not purge those historical versions.
Both commits were already pushed to `feature/007-boe-ingestion` during Task 007.

The cookies originated from unauthenticated public Bank of England statistical
requests. That establishes neither authenticated-account access nor proof that
the values are harmless, expired or unusable. No cookie/session replay, expiry
test or contact with the publisher was performed; server-side validity and
access scope remain unknown.

**Recommended owner action:** review ISS-020 before broader distribution or the
milestone PR. Treat the values as exposed and determine whether the publisher
can confirm expiry/invalidation or otherwise limit the risk. If validity or
sensitivity cannot be ruled out, approve a targeted cleanup of the affected
evidence history, coordinated with any existing clones/caches. If expiry and
limited impact are established, the owner may instead explicitly accept the
residual historical disclosure. This task does not assert that a rewrite is
mandatory or that current-file sanitisation resolves historical exposure.

[GitHub's remediation guidance](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository)
explains that revocation/rotation should precede a history-cleanup decision for
active secrets; rewriting changes commit hashes, needs coordination, and does
not remove every clone or cached copy by itself. Third-party session validity
cannot be revoked by changing this repository. No history rewrite, force push,
PR or merge is performed; owner approval is required for a separate cleanup.
