# 006.3. Task Execution Time Tracking

## Objective

Introduce lightweight, consistent execution-time tracking for all future development tasks in the UK Rental Forecasting Project.

This supports the project's AI Efficiency hypothesis by providing historical evidence of how long Codex takes to execute development tasks.

Implement this by:

1. Updating the existing `AGENTS.md` with permanent task time-tracking instructions.
2. Creating a single CSV file at `docs/task-execution-log.csv`.

Do not introduce additional tools, dependencies, infrastructure, or automated monitoring services.

## 1. Review Existing Project Instructions

Before making changes:

- Read the existing `AGENTS.md`.
- Read `docs/ENGINEERING_STANDARDS.md`.
- Review existing task numbering and documentation conventions.
- Preserve all existing instructions and approved project decisions.

This task is limited to task execution-time tracking. Do not modify ingestion pipelines, modelling code, or unrelated project functionality.

## 2. Update AGENTS.md

Add a concise section titled `Task Execution Time Tracking`.

The instructions must require Codex to:

1. Record the execution start timestamp for each development task.
2. Record the completion timestamp when the task finishes.
3. Calculate total elapsed wall-clock duration in **minutes**.
4. Use ISO 8601 timestamps with timezone information.
5. Include the duration in the final task report.
6. Update `docs/task-execution-log.csv` after each task.
7. Maintain exactly one record per task, updating the existing record when a task is resumed or revised rather than creating duplicates.
8. Use actual recorded timestamps or reliable session logs. Never invent timestamps or durations.
9. Leave unavailable measurements blank and explain any limitations in the final report.
10. Where practical, distinguish time spent waiting for user input or approval from execution time, without introducing unnecessary tracking complexity.

Execution duration should represent the elapsed time from when Codex starts working on a task until it completes or stops work.

If a task spans multiple execution sessions, record the total measured execution duration across those sessions where reliable evidence is available. Do not automatically count time between sessions as execution time.

If a task is paused, blocked, or incomplete, retain its record with the appropriate status.

Tracking should be lightweight and must not interfere with task implementation.

## 3. Create the Execution Log

Create:

`docs/task-execution-log.csv`

Use the following columns:

| Column | Description |
|---|---|
| task_id | Task number, such as 007 or 006.2 |
| task_title | Descriptive task name |
| start_timestamp | Recorded execution start timestamp |
| end_timestamp | Recorded completion timestamp |
| duration_minutes | Total measured execution duration in minutes |
| status | Completed, In Progress, Blocked, or Failed |
| timing_notes | Brief explanation of pauses, multiple sessions, incomplete measurements, or timing limitations |

Requirements:

- Express `duration_minutes` as a numeric value in minutes, allowing decimal values if appropriate.
- Use a consistent timestamp format with timezone information.
- Maintain one row per task.
- Keep the file in chronological task order where practical.
- Update existing records instead of adding duplicate task IDs.
- Leave unknown measurements blank rather than estimating them.
- Keep the file compatible with standard CSV readers and spreadsheet applications.
- Commit the CSV file to the repository as a lightweight project-management artifact.

For previously completed tasks, do not invent historical execution durations.

Historical records may be added only where reliable timing evidence is available.

## 4. Future Task Workflow

For each subsequent development task:

1. Record the start timestamp when work begins.
2. Create or update the corresponding CSV record.
3. Execute the task normally.
4. At completion, record the end timestamp and calculate the duration in minutes.
5. Update the CSV record and task status.
6. Include a short timing summary in the final Codex response.

The timing summary should contain:

- Task ID
- Start timestamp
- End timestamp
- Duration in minutes
- Status
- Any relevant timing limitations

Use the existing task documentation and reporting conventions.

## 5. Implementation Constraints

- Keep the solution simple and maintainable.
- Do not create a separate execution log for each task.
- Do not introduce a database, monitoring service, or additional dependencies.
- Do not modify existing approved engineering or methodological requirements.
- Do not overwrite existing task documentation.
- Do not retrospectively invent or estimate historical execution times.
- Avoid unnecessary scripts or automation solely to manage the CSV.

Codex may independently determine minor implementation details consistent with the requirements above.

## 6. Acceptance Criteria

The task is complete when:

1. `AGENTS.md` includes permanent execution-time tracking instructions.
2. `docs/task-execution-log.csv` exists with the agreed columns.
3. Duration is consistently expressed in minutes.
4. Unknown historical durations are not fabricated.
5. The instructions explain how to handle paused, resumed, incomplete, and multi-session tasks.
6. Future tasks can update the same CSV without creating duplicate records.
7. Existing project instructions remain intact.
8. The CSV format and tracking instructions have been checked for consistency.

Follow the existing `AGENTS.md` task-prompt archiving requirements.
